上游專案證據

  • electron-builder 官方 Auto Update：generic provider 可用，但必須自行將檔案與 metadata 發布到 Server；NSIS 是 Windows 標準自動更新路線。

v6｜Client 更新事件與伺服器集中回報（P0）

目的：Super 在 Ubuntu 後台一次看清楚每台 PC 更新到哪一步、耗時、失敗原因、檔案驗證、安裝後是否真的成功啟動；不必逐台遠端查看。

Client 本機產物用途回傳策略
update-events.jsonl逐事件結構化：每行 JSON，便於重送、排序、診斷每個階段完成即送，失敗本機暫存
update-detail.log可閱讀文字日誌；完整錯誤與堆疊，支援 Super 下載只傳摘要；故障時依需求上傳／下載完整檔
update-summary.json一次更新最終結果，機器可讀；用於 Super 清單完成或失敗時送
update-report.md方便閱讀、複製給 AI 分析的診斷報告Super 按鈕產生並下載，不必每次傳大檔

事件欄位：event_id, update_id, device_id, platform, os_version, from_version, to_version, ui_version, stage, status, timestamp, duration_ms, bytes_received, total_bytes, percent, http_status, installer_exit_code, expected_sha512, actual_sha512, error_code, error_message, reboot_required, postlaunch_ok。必要欄位固定，其餘可為 null；不要建立事件匯流排或額外服務。

{"update_id":"up-20261104-01","device_id":"PC-01","stage":"download","status":"progress","percent":75,"bytes_received":86500000,"timestamp":"2026-11-04T16:28:40+08:00"}

狀態機：check → available/no_update → download → verify → ready → install → relaunch → success；任何步驟可轉 failed，網路失聯轉 pending_report，重送使用同一 event_id 去重。安裝 ExitCode=0 不等於更新成功：需新版本重新啟動、回報版本與 UI 可用才標記成功。

上傳 API（規格草案）：POST /api/client/telemetry 同時接收 type=update 或 type=playback 的小批次 JSON；GET /api/admin/client-health 供 Super 看最新狀態；GET /api/admin/client-report/{id} 匯出報告。保留既有心跳，可在心跳夾帶摘要，避免重複 API。資料庫用 client_events 單一事件表與既有裝置表；完整日誌存檔案，不逐行寫 DB。

傳送節制：事件結束立即傳；進度每 10 秒或跨越 10% 才傳；離線先寫本機 JSONL，最多保留 7 天或 20 MB，恢復連線批次補傳。伺服器保存事件 30 天，長期只留最近結果；數值為初始預設，可由 Super 設定。單台失敗不得拖累播放器或更新程序。

05｜背景下載與檔案驗證：避免預先過度定義

先選可運作的官方路徑，不自造更新器

  1. 打包器產生 NSIS EXE、latest.yml 與相應 blockmap；同一次建置生成，不能混搭。
  2. Ubuntu Nginx 直接提供同來源更新檔案，支援 GET／HEAD，差異下載如需 Range 再確認。
  3. Client 使用與該 Electron 版相容的 electron-updater；檢查新版、下載並使用 metadata 內 SHA-512 驗證。
  4. 先在 Win10 真正安裝版測「舊版→新版」，不可用下載成功或 registry 版本當作完整自動更新成功。
  5. 差異更新可省頻寬，但不以此為首要目標；失敗可退回完整下載。七台 LAN PC 全量 EXE 更新負擔通常可接受。
  6. 更新完成後等影片播放結束，使用 next-launch 或等價方式安裝；禁止關機途中強制更新。

安全範圍：必要且克制

保留來源固定、安裝包完整性校驗、基本角色權限、受限 IPC。若所選新版 electron-builder／updater 強制要求簽章 manifest 或 Windows 簽章，先記錄版本限制與可行選項，再由 Super 決定採用的工具版本與最小措施；不得為此自行開發 PKI／憑證中心。SHA-512 是完整性校驗，不等於證明發布者身分。是否可在目標 Windows 上免 UAC，須依 NSIS per-user 安裝模式實測。

不可直接宣稱成功的情況

latest.yml 200、EXE 200、SHA-512 正確、手動 /S 安裝成功，都只算部分 PASS。真正 PASS 必須包含「已安裝舊版自動偵測→背景下載→校驗→閒置安裝→自動重啟→UI/登入/影片可用→Server 收到新版本心跳」。

06｜重點 KPI：七台影片預讀與有限快取

目標與非目標

目標：七台同時播放、快轉、暫停恢復時流暢；Client 可保留適量已下載片段，避免短暫 LAN 波動重抓。非目標：整部 12TB 媒體庫同步、永久離線觀看、複雜 P2P/CDN 或 DRM 系統。

B｜必要才做受控區段磁碟快取（分片／大小上限／LRU／過期／權限檢查）七台實測顯示網路抖動、反覆拖曳導致重複下載且 A 不足

關鍵技術限制

  • HTML5 video 的 preload=auto 只是提示，不保證預載多少；Chromium 快取行為也不等於可保證的離線磁碟快取。
  • HTTP Range 必須支援 206 Partial Content、Content-Range、Accept-Ranges、416；驗證權限後由 Nginx 送影片，不用 PHP 逐位元組傳 7 份。
  • MP4 使用 H.264/AAC 並將 moov metadata 前置（faststart）；先 Direct Play，避免七路即時轉碼。
  • 若進入 B，預設建議上限例如每台 1–2GB（待實測決定，非硬性規格）；優先快取正在看及即將看的片段，LRU 清除；快取不授權離線播放。
  • Web UI 更新不能清除當前播放緩衝；播放器不得因心跳或 UI 新版強制重整。

量測與驗收

指標量測方法通過條件
七台同步播放七台真機同時 1080p，不同影片／同一影片各測播放期間無持續轉圈或頻繁停頓；記錄原因

v6｜播放 QoE（Quality of Experience）日誌與七台集中分析（P0）

播放流暢度不能只看 Nginx 200/206 或網速；要由 Client 直接量測使用者實際看到的播放情況。以原生 HTML5 video 的 waiting、stalled、playing、seeking、seeked、error、getVideoPlaybackQuality()、buffered 與 currentTime 取得資料；不引入新播放器或大型監控平台。

指標計算／說明警示建議（可調）
首次播放等待按播放到第一個 playing 的毫秒數> 3 秒標示需注意
非使用者操作卡頓次數playing 後 waiting/stalled，排除手動暫停、seek、結束每 10 分鐘 ≥ 2 次
卡頓總秒數與比率卡頓時間／實際觀看時間，合併重複事件比率 > 1%

快轉恢復時間seeked 後至 playing／可持續播放> 3 秒
傳輸／錯誤影片 ID、畫質、HTTP 錯誤、播放器錯誤碼、Client OS、版本有錯誤即顯示

採樣規則：播放中每 15 秒取樣本機累積數據；每 60 秒或影片結束回傳一次摘要；卡頓／錯誤事件即時記錄，避免每秒呼叫 API。離線補傳；單次上傳失敗不影響播放。播放會話使用 session_id，不記錄影片原始檔案內容。

{"type":"playback","device_id":"PC-01","session_id":"s-001","media_id":"m-42","duration_s":600,"startup_ms":1280,"rebuffer_count":1,"rebuffer_total_ms":900,"dropped_frames":3,"total_frames":18000,"buffer_ahead_s":18.5,"cache_hit_bytes":0,"timestamp":"2026-11-04T21:00:00+08:00"}

預讀／快取驗證：另記 cache_mode, cache_bytes, cache_hit_bytes, cache_evictions, range_requests, network_error_count；先區分 Chromium 內部 buffer 與真正可控的磁碟區段快取，不能把 buffer 誤報成快取命中。若未實作磁碟快取，命中欄位標 null 而非虛構數值。

09｜安全設計上限：Super 指定、禁止擴張

封閉 LAN、小型內部系統的最小必要安全

本章為後續 AI 開發的限制條款。不得自行把安全議題升級成多週大型工程，也不得擅自增加 SSO、OAuth、憑證中心、微服務隔離、完整零信任或額外監控平台。

  • 保留現有登入與 Super/Admin/一般會員權限；Admin 後端只能使用授權的 USB 匯入 API，不能只隱藏 Tab。
  • Electron 遠端 Web UI：nodeIntegration:false、contextIsolation:true；只開必要的 preload 方法；不允許網頁任意執行命令。
  • 固定 iSTUDY LAN 來源；下載的安裝檔至少驗證 manifest 與 SHA-512；若上游套件版本另有硬性要求，先告知 Super 決策。
  • root 系統操作只由預先定義的 systemd 受控動作執行，不提供通用 root 終端機給 Web。
  • 其他安全強化列為「選配」，除非已發現明確風險或使用者要求，不得擅自加入開發範圍。

現實界線：LAN 並非絕對安全，且 SHA-512 不等於可信來源認證；因此保留上述基本防護，但不藉此擴張成新平台。

13｜Page Atlas × PostgreSQL × Tab 可視角色

採用資料庫管理，不再只做靜態頁碼表。Page Atlas 只保留頁碼、頁名、來源定位、最簡導覽及 Tab 角色可視性；不引入截圖版本庫、元件依賴圖、程式碼 AST 分析、額外搜尋服務。

角色規則（固定）

  • Super 永遠可見所有 Tab，不可取消，不出現在角色勾選欄位。
  • Super 後台設定表每列為一個 Tab，只有 Admin、User 兩個勾選框。
  • 預設新 Tab：Admin=false、User=false；Super 仍可見。
  • Tab 可視性是 UI 入口權限；若 Tab 連結管理 API，後端也須依相同角色檢查，不得只隱藏按鈕。
  • Admin USB 匯入頁面預設 Admin=true、User=false；Client 學習頁依需求設定 User=true。
  • 權限只控制角色可見性；課程／影片個別授權仍由原有課程權限機制負責，兩者不可混為一談。

14｜PostgreSQL：維持不換，建立全新乾淨資料庫

決策：維持 PostgreSQL，優先使用 Ubuntu 已有的 PostgreSQL 18。七台影片播放瓶頸主要在 HTTP 傳送、Client 解碼與網路，不在 PostgreSQL 換牌。PHP/Python 已具備 PostgreSQL 使用經驗，改 MySQL 或 SQLite 只會增加遷移及重新驗收成本。

全新建庫的規則

  1. 先列出主機上 PostgreSQL 的既有資料庫與使用者，不得刪除其他專案 DB。
  2. 建立全新的 iSTUDY 專用 DB 與帳號，使用全新 schema migration；不從 Dev63 舊 DB dump 全量還原。
  3. 新 DB 只由目前核准的功能清單推導資料表；禁止為了兼容舊版建立 legacy、v1/v2、deprecated、tmp_* 等表或欄位。

  5. 舊 iSTUDY Docker PostgreSQL／Volume／DB 僅在新系統驗收後，依確認的刪除清單清理；先確認備份與所有權，避免刪到其他專案。

16｜防止再次過度開發：不可偏離的規則

  1. 目標：七台 Client 流暢播放、Super/ Admin UI 可用、零日常終端機、更新免逐台維護；其他不是優先目標。
  2. 不得擅換技術：Electron、React、Nginx、PHP、PostgreSQL、Python Worker、systemd、FFmpeg、FunASR、LibreOffice；Jellyfin 禁止。
  3. 不得新增基礎設施：Docker、Redis、RabbitMQ、Kubernetes、微服務、獨立監控平台、額外 DB、複雜安全框架；需要新增先說明理由並取得同意。
  4. 不要求 Git 工作流：本機不強制 git init/commit/branch；GitHub 不開 PR、不自動合併。使用有版號的完整交付包、校驗碼與備份，保留可回退版本。
  5. 安全範圍：封閉 LAN、單一 Super；保留登入、角色檢查、資料庫權限、固定本機維護命令、更新檔案驗證與必要的 Electron 隔離。不得自行擴張成大型權限/稽核/簽章平台；任何額外安全功能先請示 Super。
  6. 驗收三層：每次更新做 2–5 分鐘基本 health；變更功能做對應小測試；首次重建或重大改動才做七台播放、Win7/10/11/Ubuntu 安裝、USB 匯入、轉檔/ASR/Office、更新與回退的完整 E2E。
  7. UEM 保留核心：健康檢查、功能冒煙測試、日誌、診斷下載、備份/恢復、版本/服務狀態、關鍵轉檔與字幕 QC；不複製舊 UEM 過度複雜的測試編排。
  8. Page Atlas：只有兩張表、基本頁面資訊、Admin/User 可視性及最簡導覽；不得擴張為多表元件追蹤系統。
  9. 不留舊包袱：新 DB 只建新表；新系統驗收後清理舊 iSTUDY 專用容器、腳本、DB 與相容層；不得影響其他專案。
  10. 不得宣稱未驗收已完成：Win10 手動安裝通過不等於背景自動更新 E2E 通過；七台影片快取、Win7 新版 UI、原生 Worker 都要有實測結果。

每次改動的固定簡短交付

只交付：①改了哪些檔案／功能；②是否改 DB/API；③對應測試 PASS/FAIL；④更新包與校驗碼；⑤若失敗如何回復。禁止每次重寫整份計畫書或產生大量無關報告。

v6｜新增強制交付驗收

  2. Client 一次安裝能留下四份診斷原始檔；首次啟動可補報，Super 可下載 MD。
  3. UEM 每項有新位置與測試結果；不得只保留名稱卻刪功能。
  4. Super WOL 三子 Tab、Client 登入前公開喚醒、設備清單公開設定三欄均需實際驗證。

  6. 日常更新不得新增 Git／PR／CI 前置要求，不得新加監控平台、消息佇列、微服務。
